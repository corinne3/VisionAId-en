# Decision log

> English translation of the team's [`DECISIONS.md`](../../DECISIONS.md). The French original is the reference. File names, session names and config keys are kept as in the code (`gourde` = water bottle, `clés`/`cles` = keys, `couloir` = corridor, `piece` = room, `carte` = map, `monde` = world).

Format: date — context — choice — rejected alternative.

- **2026-11-21 — Input data** — The files provided are `assets/IMG_0270.MOV` (HEVC 1920×1080, 90° rotation, 16.2 s, 30 fps) and two HEIC photos. The video stream is copied without re-encoding to `data/video/appart.mp4` (rotation metadata kept, to exercise rotation handling) and the HEICs are converted to `data/ref/gourde_{1,2}.jpg` with `sips`. — Rejected: re-encoding to H.264 while applying the rotation (quality loss, and the rotation test would become trivial).
- **2026-11-21 — Python version** — The initial repository requires Python 3.12 (`.python-version`, `requires-python>=3.12`). 3.12 is kept instead of the plan's 3.11: all dependencies are available. — Rejected: downgrading to 3.11 (no benefit).
- **2026-11-21 — open3d** — open3d 0.20 (macOS arm64 wheel) depends on a missing `/opt/homebrew/opt/libusb`; installing through Homebrew is outside the allowed network scope. Second attempt: open3d 0.19, which works. Constraint `open3d<0.20`. numpy forced to 2.x (pyarrow, required by rerun, needs numpy ≥ 2).
- **2026-11-21 — Config as dataclasses** — Config dataclasses are generated dynamically from the YAML (`dataclasses.make_dataclass`), with attribute access `cfg.section.key`. — Rejected: hand-writing ~20 dataclasses duplicating the YAML (risk of getting out of sync).
- **2026-11-21 — ZeroMQ HWM** — 1,000 messages sent in a burst with HWM=1000 on send and receive lost the last message. Default HWM raised to 10,000 for light streams (conflate mode is not affected). — Rejected: application-level flow control (unnecessary at these rates).
- **2026-11-21 — Bus envelope** — Single-part ZeroMQ message `topic|t_send(float64)|msgpack`: ZMQ_CONFLATE does not support multi-part messages; one socket per topic in conflate mode. The wall-clock send timestamp makes it possible to measure input age.
- **2026-11-21 — CLIP tokenizer for YOLOE** — Ultralytics wants to install the `clip` package from GitHub (refused by the environment policy: outside pip/uv/HF). YOLOE only uses `clip.clip.tokenize`; `perception/clip_shim.py` provides an equivalent tokenizer through `transformers.CLIPTokenizer` (same BPE, context 77, identical ids). The MobileCLIP2 text encoder comes from the Ultralytics assets. — Rejected: falling back directly to COCO YOLO "bottle" (loss of open vocabulary).
- **2026-11-21 — Expired Hugging Face token** — An expired "hackathon" HF token is configured on the machine and makes even public downloads fail. `visionaid/__init__.py` sets `HF_HUB_DISABLE_IMPLICIT_TOKEN=1` (all models used are public). **To do by you**: renew or remove this token (`hf auth logout`).
- **2026-11-21 — Detector** — YOLOE-26s-seg (`yoloe-26s-seg.pt`) available and chosen; low confidence threshold (0.10) because ReID filters afterwards. The YOLOE-11 → YOLO-World → COCO fallbacks are coded but not exercised. YOLOE visual prompt not enabled (`use_visual_prompt: false`): specificity comes from ReID; to try in phase 12.
- **2026-11-21 — Colour model** — Under the apartment's warm lighting, the bottle's stainless steel has H≈17-22 and S≈80-156: a "grey" defined by S ≤ 50 does not capture it. Orange = H∈[5,30], S≥150, V≥100; grey/metal = S≤140, V≥50 (measured on the reference photos).
- **2026-11-21 — Multiplicative ReID score** — With an arithmetic mean 0.6·embedding + 0.4·colour, the bottle tinted blue passed the threshold (DINOv2 is not very sensitive to hue). Score = weighted geometric mean `emb^0.6 · colour^0.4`: a missing colour cancels the score. The shifted-hue test passes.
- **2026-11-21 — Calibration negatives** — The bottle appears in the video: the best-scored "negatives" were the bottle itself. Exclusion rule: DINOv2 similarity ≥ 0.60, or ≥ 0.45 with colour score ≥ 0.5. Side effect: 3 crops of an orange bag (sim 0.46-0.48) are wrongly excluded. Calibrated threshold (max F1): 0.575; remaining negatives max 0.53.
- **2026-11-21 — Tracker appearance gating** — Bug found by the colour check: when the bottle was not detected, its confirmed track jumped onto the cereal box next to it. A confirmed track can no longer match a detection with score < 0.6×threshold, and a detection is only designated "target" if its score ≥ 0.85×threshold.
- **2026-11-21 — Video colour check** — Interpretation of "incompatible dominant hue": among saturated pixels (S≥80), if > 25% of the mask is saturated and the dominant hue is not in [0,35]∪[170,180] (red/orange/brown), it is incompatible. A first criterion "no orange pixel" wrongly flagged the partly visible bottle (top only, close-up in hand).
- **2026-11-21 — Depth backend** — Depth Anything 3: not supported by `transformers`; the PyPI package `depth-anything-3` (0.1.1, author "Your Name", unofficial) forces numpy 1.26 (breaks rerun/pyarrow) and xformers (CUDA). Attempt abandoned, planned fallback: **Depth-Anything-V2-Metric-Indoor-Small** (125 ms/frame at 518 px on MPS; Base: 323 ms for almost identical values). The DA3 backends stay in the fallback chain and fail cleanly.
- **2026-11-21 — Scale** — Bottle height estimated at 0.33 m for 0.25 m (+32%, within the ±40% tolerance): no scale factor applied (`depth.scale_factor: 1.0`). The bias may come from depth or from the assumed field of view (69°). Suggested factor if needed: ≈ 0.76.
- **2026-11-21 — "Per pair" VO accuracy** — With 0.5 px noise and 3.4 cm steps between frames, even an oracle PnP (exact 3D structure) has 0.5-1.5 mm error, i.e. 2-4%: the "< 3% per pair" criterion is at the noise floor if "pair" = consecutive frames. Interpreted as **consecutive keyframe pairs** (baseline ≥ 0.15 m, which the VO estimates directly): median 1.2% (2.1% with 30% outliers), rotation < 1° everywhere. Additional per-frame safeguard: median < 15%, rotation < 1°. Rotation and drift thresholds unchanged.
- **2026-11-21 — VO** — Minimal-sample RANSAC with AP3P (robust to ~50% wrong matches when the keyframe and the current frame each have 30% outliers), then LM refinement and **symmetric refinement** (reprojection keyframe→current and current→keyframe with the current depth, Huber loss). Open3D fallback (`compute_rgbd_odometry`) if PnP fails. Pose graph optimisation not done (optional).
- **2026-11-21 — numpy warnings** — numpy 2.x + Accelerate (macOS arm64) emits spurious `RuntimeWarning: ... encountered in matmul` (results correct, checked finite). Filtered in `visionaid/__init__.py` and `pyproject.toml`.
- **2026-11-21 — Depth scale factor 0.76** — Phase 4 passed (+32%), but 3D fusion confirmed the bias: camera height 1.84 m and bottle 1.15 m above the floor. With the factor 0.25/0.33 ≈ 0.76 estimated on the bottle: camera at 1.39 m (σ = 8 cm), bottle at 0.87 m (table ≈ 0.75 m + half bottle). `depth.scale_factor: 0.76` (the cache stores raw depth).
- **2026-11-21 — Costmap height bands** — The measured floor (after alignment) spreads over ±7 cm (monocular depth noise). Obstacle band of the plan [0.05; 1.90] → **[0.10; 1.90]**, floor band ±5 cm → **±8 cm**, plus a tolerance of 4 cm per metre of distance (`obstacle_height_slope`). Otherwise the noisy floor was marked as an obstacle.
- **2026-11-21 — Costmap forgetting** — A decay of 0.97 per update (half-life < 1 s at 30 Hz) erased the whole map outside the last 2 seconds. Forgetting is now in real time: half-life 20 s (`decay_half_life_s`). Removed obstacles are mostly freed by ray casting (test: < 15 updates); forgetting alone takes < 100 updates at 1 Hz.
- **2026-11-21 — World frame** — Origin on the floor below the first camera, z = floor normal, x = initial camera heading projected on the floor, y = z × x (to the left). The floor plane is estimated continuously (α = 0.05) with outlier rejection (> 10° or > 30 cm).
- **2026-11-21 — Planning in numba** — A* in pure Python: 38 ms on 200×200 (too close to 50 ms) and initial D* Lite of several seconds on the real costmap (~67,000 cells). Added `numba` (PyPI): A* 2.9 ms, D* Lite 8 ms cold and 1.9 ms incremental, identical to A* over 150 replans. Step cost = length × (1 + mean cost of the two cells), no diagonal corner cutting, unknown = +3 ("cautious optimist").
- **2026-11-21 — Planning goal** — Traversable cell closest to the object (preferably free, radius 1.5 m); at equal distance (±1 cell), the one closest to the user. If the user is themselves in an inflated zone (noise or nearby furniture), the start is the closest traversable cell (≤ 1 m).
- **2026-11-21 — Guidance: universal hold time** — The plan requires ≤ 1 state change per 0.3 s: the hold time applies to all transitions, including entering `OBSTACLE_ALERT`/`TRACKING_LOST` (alert latency ≤ 0.3 s). Near the target (< 1.2 m), the furniture carrying it does not trigger an obstacle alert. Positive azimuth to the left; a 2D target (look-ahead point on the floor) is taken at head height (zero elevation).
- **2026-11-21 — Binaural audio** — Parametric model only (Woodworth ITD, Brown & Duda 1998 head shadow, 2.5 kHz low-pass weighted for the rear); SOFA/KEMAR not attempted (`sofar` not in dependencies, `use_sofa: false`). Per-sample processing in numba, azimuth smoothed on the circle (τ = 50 ms), smoothed gains (10 ms): no clicks. "No click" test: maximum sample jump ≤ 1.5 × that of the two steady states (0° and 90°); the HF gain at 90° on the ear side makes a comparison with the 0° steady state alone irrelevant.
- **2026-11-21 — Simulator: agent model** — Reaction delay 0.3 s, heading noise σ = 10° (resampled every second: persistent error rather than jitter), 0.6 m/s. The agent only moves forward if the heading error is < 30° (it turns first: with 60°, it slid sideways against obstacles). During an alert, it stops and moves away from the sound, in a direction chosen when entering the alert and then kept (otherwise it oscillates in front of a wall). Collision = centre at < 0.20 m from an obstacle (half shoulder width).
- **2026-11-21 — Guidance, fixes from the simulator** — (1) Look-ahead point constrained to the line of sight from the user's real position on a "body corridor" grid (clearance ≥ 0.25 m): otherwise the chord cut corners. (2) Obstacle alert limited to the corridor swept by the body (|lateral offset| < 0.25 m) within the ±30° cone: an obstacle beside a clear path no longer triggers an alert. (3) No alert in `SEARCHING` (rotating on the spot). (4) In `APPROACHING`, guidance along the end of the path while the goal is > 0.30 m away, then straight to the object (direct guidance bumped into furniture corners). Result (100 seeds): room 95% / 96% without collision, corridor 94% / 96%, sudden obstacle 96% / 99%.
- **2026-11-21 — Simulator scenarios** — Room: object on a piece of furniture, near the edge, visible at ≤ 4 m from the start (the user is in the room). Corridor: object in the other room, already in memory ("find the bottle left over there"). Sudden obstacle: 0.6 m box at ≥ 1.3 m ahead after 4 s (closer, collision is physically unavoidable with a 0.3 s reaction); placed in ~72% of episodes, the replanning criterion is computed on those. Validity: reachable with the same radius (0.35 m) as the planner.
- **2026-11-21 — Real map in the simulator** — The costmap from the video is too cluttered (monocular noise, chairs, a seated person): even with a 0.25 m body radius, the start and the arrival zone are in two disconnected components. "Real map" scenario cannot be evaluated (cleanly skipped). Leads: ARKit/LiDAR depth, better fusion (TSDF), stricter occupancy thresholds.
- **2026-11-21 — 100-seed simulator test marked `slow`** — No model, but ~3 min on 9 cores: it goes into the `slow` suite; a smoke test (5 seeds per scenario) stays in the fast suite. Thresholds unchanged.
- **2026-11-21 — Real time** — 7-process graph: source (1× replay, looping beyond 16 s), perception, geometry (depth + VO in the same node, the VO needs the depth of the same frame), world, planner (5 Hz), guidance (20 Hz timer on the latest inputs), sink. Heavy nodes read the latest frame (conflation); the world node matches the closest detection within ±3 frames (otherwise only 16% of updates had a detection). Masks compressed (packbits) on the bus. End-to-end latency measured = arrival of the instruction − replayed capture time, counted once per frame. Result: p50 ≈ 360-390 ms, p95 ≈ 440-690 ms (> 300 ms targeted). Bottlenecks: geometry 170-190 ms (DAv2 depth ~130 ms competing for the GPU with YOLOE + VO), mapping ~90 ms (back-projection + ray casting + distance transform). Leads: DAv2 at 364 px, CoreML export of YOLOE, incremental costmap, cost computed only by the planner.
- **2026-11-21 — Rerun** — Full-resolution depth on every frame: 648 MB. Now image every 2nd frame (JPEG), depth at ¼ resolution every 6th frame, point cloud every 10th frame, costmap every 10th frame: 46 MB.
- **2026-11-21 — Obstacle alert on the video** — The offline run spends 7.3 s in `OBSTACLE_ALERT` (from 3.5 to 10.8 s): the person brushes past a chair then walks along the table; the alert is largely legitimate (checked on the annotated frames), but no `NAVIGATING` appears on this video. To be analysed with a real user.
- **2026-11-21 — Phase 12 (optimisations)** — CoreML export of YOLOE-26s-seg succeeded (39.8 MB, `.cache/weights/yoloe-26s-seg.mlpackage`) but **not kept**: 25/26 detections matched (IoU > 0.5) with a median score difference of 5.8% (p90 19.6%, beyond the criterion's ±5%) and a lower throughput (17.5 vs 57 fps with PyTorch MPS, square 640×640 input required). `coremltools` removed from dependencies. DA3-Small and pose graph optimisation not done (DA3 unavailable, see phase 4; time spent on phase 10).
- **2026-11-21 — Phase 14: body frame in camera convention** — The plan described the body frame as x forward / y left / z up. The existing guidance code reads `T_world_head` in camera convention (z = forward). To break nothing, `body.T_cam_body` is expressed in camera convention (identity = phone upright on the chest) and replaces `guidance.T_cam_head` when present. Rejected: changing convention and adapting guidance, no benefit for this step.
- **2026-11-21 — Phase 14: frame header in JSON** — The plan specified a msgpack header. The web page is plain JavaScript, with no library or CDN: the header is JSON (`TextEncoder`), prefixed by its length on 4 bytes. The cost is negligible (~80 bytes per frame).
- **2026-11-21 — Phase 14: gyroscope sent raw** — The page sends `rotationRate` as is (`[beta, gamma, alpha]`, deg/s according to the specification) and announces the unit in `hello`. Conversion to rad/s is done by the server, and phase 17 checks units and axes on real data.
- **2026-11-21 — Phase 15: acknowledgement after ingestion** — The computer acknowledges a frame after decoding it and passing it to processing, not on receipt. The phone can therefore never go faster than the computer, and the next frame is grabbed when the computer is ready: frame age p95 < 2 periods even with a consumer 2.5× too slow (test).
- **2026-11-21 — Phase 15: RTT matched by identifier** — The first version associated a ping's delay with the RTT of the previous exchange: a ~10 ms bias detected by the test. The ping now carries `prev_id` + `rtt`, and the computer matches delay and RTT of the same exchange.
- **2026-11-21 — Phase 15: fake phone inside the package** — The plan put it in `tools/fake_phone.py`; it is in `src/visionaid/phone/fake_phone.py` (`python -m visionaid.phone.fake_phone`) so that tests and the real-time graph can import it without touching `sys.path`.
- **2026-11-21 — Phase 15: web page not testable automatically here** — The built-in browser refuses the local authority's certificate (expected behaviour) and there is no phone: the page is checked with `node --check` and served (HTTP 200), the protocol logic is covered by the fake phone. Real validation is in the checkpoint checklist.
- **2026-11-21 — Phase 16: frame index = `seq`** — A session frame keeps its send number `seq` as `frame_idx` (identical live and in replay), instead of a 0..N counter. Gaps in numbering (calibration frames, losses) have no effect: `frame_idx` is only used as a matching key.
- **2026-11-21 — Phase 16: real-time replay time** — `SessionReplayBlock` brings frame and IMU times back to the start of the session, with the same offset for both, like the video time of `ReplaySourceBlock`. The existing latency measurement (wall-clock start time + `t`) therefore remains valid. `t_phone` keeps the original clock.
- **2026-11-21 — Phase 17: visual rotation with a "pure rotation" model** — To compare with the gyroscope, the rotation between two frames is estimated by RANSAC + Kabsch on the directions of matched points (0.6° threshold). The essential matrix is ill-conditioned when translation is almost zero (rotation on the spot, precisely the calibration motion). A small translation (phone on the chest) only eliminates near points as outliers.
- **2026-11-21 — Phase 17: time offset by norm correlation** — δ is searched over ±300 ms (5 ms steps then 0.5 ms) by correlating the gyroscope norm averaged over the interval between two frames with the norm of the visual angular velocity. Since the norm does not depend on the unknown rotation, δ can be estimated before `R_cam_imu`. Averaging over the interval, rather than sampling in the middle, avoids a bias at varying speeds.
- **2026-11-21 — Phase 17: device identified by the config** — Safari iOS does not give the iPhone model in the user agent. Calibrations are therefore stored under `phone.device` (default `iphone12`) and not inferred from the user agent as the plan specified. The user agent is recorded in each calibration file.
- **2026-11-21 — Phase 17: distortion not corrected** — Distortion is estimated and saved, but the pipeline stays pinhole: the iPhone wide-angle camera already strongly corrects distortion in video. To revisit if the real reprojection error justifies it.
- **2026-11-21 — Phase 18: VIO by composition, without a Kalman filter** — The gyroscope provides the predicted rotation (PnP seed, 8° consistency check, fallback when VO drops out) and the accelerometer the vertical (complementary filter, gain 0.05, corrections ignored if ‖a‖ differs from g by more than 1.5 m/s²). Position stays entirely visual: double integration of a phone accelerometer drifts within a few tenths of a second. Rejected: a full EKF/MSCKF, too long for the hackathon and hard to validate without ground truth.
- **2026-11-21 — Phase 18: `degraded` state** — VO lost but gyroscope available: orientation propagated, position frozen, quality `degraded` for at most 2 s (`vio.degraded_max_s`), then `lost`. Guidance continues (orientation is right); mapping and target anchoring are suspended (position would be wrong if the user walks).
- **2026-11-21 — Phase 18: where the gain in fast rotation comes from** — In the synthetic test, blur is modelled by losing almost all points (15 instead of ~300). VO then drops out on 55% of frames, and the gyroscope seed cannot prevent it: without points there is no PnP. The gain (0% `lost`) comes from the gyroscope fallback. On real data, the seed should also help when enough points remain. This will be measured on `rotations_rapides`.
- **2026-11-21 — Phase 18: floor constrained by gravity** — When the pose carries `up`, the floor normal is imposed by gravity and RANSAC only provides the floor height. The tilt of the freely fitted plane is kept as a check (`FloorTracker.tilts_deg`). Without `up` (video without IMU), phase 6 behaviour is unchanged.
- **2026-11-21 — Phase 18: scale from camera height** — The factor s = declared height / measured height is measured on the lower half of the image: the floor is the lowest dense mode along gravity. It is smoothed in log space (EMA 0.1) and bounded to [0.5; 2]. It applies on top of `depth.scale_factor`. For phone sessions, this fixed factor (0.76, calibrated on the old video) is therefore corrected automatically.
- **2026-11-21 — Phase 18: accumulating IMU inputs on the bus** — The generic node only kept the last message of each topic: IMU batches arriving between two processed frames were lost. `NodeSpec.accumulate_inputs` now delivers all messages received since the last call, as a list (`Subscriber.drain_all`).
- **2026-11-21 — Phase 19: target cards = config overrides** — A card (`config/targets/<name>.yaml`) contains its trigger phrases and an `overrides` block applied to the config: YOLOE prompts, reference photos, colour model, ReID threshold. Resolution is done in `load_raw` as soon as `target.query` is set, and explicit overrides (command line, tests) take precedence over the card. The default config stays the bottle one: no behaviour change without `--target`.
- **2026-11-21 — Phase 19: phrase → card matching** — Normalisation (lower case, accents, punctuation), removal of stop words ("où", "est", "ma", "mes", "trouve"…), approximate singular. First an exact match with a card phrase is searched, then a card one of whose phrases is contained in the query. If no card or several match ("ma gourde et mes clés" — my bottle and my keys), the error lists the known targets.
- **2026-11-21 — Phase 19: keys** — No colour model (metal, reflections): `color_model: none`, ReID score = embedding only. Without `cles_*.jpg` photos, "text only" mode: the score is the YOLOE confidence and the threshold `reid.textonly_conf` (0.25). Limit: two objects of the same category are not distinguished. Detection threshold lowered to 0.08, because the object is small and ReID filters afterwards. No real figures as long as the `cles_piece` session is missing.
- **2026-11-21 — Phase 19: perception cache key** — The new fields `reid.color_model` and `reid.textonly_conf` change the config fingerprint, so the video's perception cache is recomputed once. The phase 3 negatives cache is reused for the bottle.
- **2026-11-21 — Phase 20: timer-driven planner with a watchdog** — The planner was triggered by the costmap: without a new frame it no longer ran and the last path stayed displayed. It now runs at a fixed rate (5 Hz). It only replans on a new costmap, and publishes an **invalid** path (once per second) if no fresh pose has arrived for 1.5 s or if the pose is lost. Future guidance will therefore never have to follow a stale path.
- **2026-11-21 — Phase 20: end-to-end latency measured** — Measure = path publication time (computer) − frame capture time brought to the computer clock (`t_phone + offset`, ping/pong synchronisation). It therefore includes JPEG encoding, the local network, decoding, perception, geometry, world and planner. In session replay, the reference is the replay start time, as in phase 11.
- **2026-11-21 — Phase 20: fake phone IMU on the real video** — `appart.mp4` has no IMU. The gyroscope is derived from the visual rotation between frames, which makes it consistent with the video. The accelerometer is sent as **zero**: the video's real vertical is unknown and an invented gravity would distort the floor. Gravity therefore does not initialise, and floor and scale stay those of phase 6 (factor 0.76). The test exercises transport, gyroscope and latency, not gravity, which will only be validated by real sessions.
- **2026-11-21 — Phase 20: bugs found by the full graph** — Scale re-anchoring never activated on a perfectly flat floor, for two reasons: a one-sided histogram, and smoothing that selected an empty interval. Both are fixed, with a dedicated test. The real case (noisy floor) was not affected, but the graph test revealed it.
- **2026-11-21 — Phase 21: 364 px depth not kept by default** — Measured on the fake phone replaying `appart.mp4` (real models, 30 s): capture → path latency p50/p95 341/429 ms at 518 px against 209/275 ms at 364 px, geometry 5.4 vs 10.6 Hz. But on the full offline pipeline, guidance consistency goes from 7° to 46° (median) and the final distance from 0.18 to 0.35 m: coarser depth degrades the map and the path. Latency at 518 px already meets the 700 ms target, so accuracy wins. The `--depth-width 364` option remains available.
- **2026-11-21 — Phase 21: depth every N frames, incremental costmap, WebRTC** — Not done. RGB-D VO needs depth on every processed frame, so skipping depths requires an intermediate monocular VO, beyond the available time. Mapping (~90 ms) is no longer the first bottleneck once depth at 518 px stays under the target. WebSocket JPEG transport adds a few milliseconds locally: WebRTC would bring nothing measurable here.
- **2026-11-21 — First iPhone trial: certificate and network change** — Team feedback: "connection not private" on Wi-Fi, "cannot connect" on Personal Hotspot. Cause found on the computer side: the server had been started on the hotspot (certificate for 172.20.10.5), then the Mac switched to Wi-Fi (10.5.60.177), an address not covered by the certificate. The server now checks the address every 3 s and re-issues its certificate on the fly with the same authority, without restart or reinstallation. The fake phone of `run_live` takes a free port, so that it never connects to a real server already running (this had happened in `night_run`).
- **2026-11-21 — IPv6-only 5G hotspot** — Second iPhone trial: "your iPhone is not connected to the Internet". The hotspot (operator Orange) is IPv6-only: macOS only has a translation IPv4 (`192.0.0.2/32`, CLAT), unreachable from the phone, and the server only listened on IPv4. The server now listens on all interfaces in IPv4 and IPv6 (`phone.host: auto`). Global IPv6 addresses are added to the certificate. The URL shown first is the Bonjour name `<mac>.local`, which works in both cases. Translation addresses 192.0.0.0/29 are no longer offered. Checked on the machine: HTTPS with full certificate verification through `.local` and the IPv6 addresses.
- **2026-11-21 — Real iPhone 12 data: units entered in cm** — The camera height was entered as `150` (cm) and the square size as `Case =2.2cm`. Entered lengths are now interpreted according to their order of magnitude (`length_to_m`: > 3 → cm, > 300 → mm), and notes accept mm, cm or m. The height recorded in each session takes precedence over the config on replay. Data files are not modified.
- **2026-11-21 — Safari iOS: gyroscope axes and accelerometer sign** — Real calibration (correlation 0.996) shows that Safari iOS sends `rotationRate` with alpha/beta/gamma around x/y/z, and not z/x/y as the specification says. It shows up as a 119° rotation of `R_cam_imu` relative to the prior: a cyclic permutation of the axes. `accelerationIncludingGravity` has an inverted sign (−9.7 m/s² upward, phone upright). The calibrated gyroscope rotation therefore no longer applies to the accelerometer. The accelerometer keeps the specification axes, with a sign measured on still segments (`accel_sign`, phone in portrait at rest). The page is not modified: the correction is measured, and also applies to sessions already recorded and to other browsers.
- **2026-11-21 — Scale: the table taken for the floor** — On `gourde_piece`, the factor climbed to 1.6. When the camera points at the table, the table top dominates the bottom of the image and the floor is only a secondary mode, eliminated by the relative threshold (30% of the main mode). Three fixes: floor = lowest surface with a sufficient **absolute** number of points, rejection of measurements that change the factor by more than 30%, start on the median of the first 5 measurements. Factor now 1.09 (gourde_piece) and 0.93 (rotations_rapides). Independent check from the bottle size: 0.30 m measured for 0.25 m real with the base factor (implicit factor 0.84). About 25% difference remains between the two methods, which is consistent with non-linear monocular depth (bottle at 1-2 m, floor further away).
- **2026-11-21 — Real rate ~10 fps** — The iPhone 12 sends about 10 frames/s instead of the 15 requested: canvas grab, JPEG encoding and acknowledgement for each frame, with 40 ms median age. It is enough today (geometry runs at ~6 Hz); to revisit if the processing chain gets faster.
- **2026-11-21 — Synthetic tests isolated from the real calibration** — Once `config/calib/iphone12_*.yaml` were created, three synthetic tests (sessions and graph with stubs) loaded the real iPhone calibration (inverted accelerometer, different K), incompatible with their simulated data that follows the specification. They now point `phone.calib_dir` to an empty folder. No threshold changed.
- **2026-11-21 — Phase 23 (A): probable target** — On `gourde_piece`, the bottle is detected from 8.5 s, at about 5 m, but its ReID score from afar (0.44-0.56) stays under the 0.575 threshold: it was only confirmed at 20 s. A track now becomes a **candidate** if its score exceeds 0.85 × threshold (0.49) on at least 5 consecutive frames, as long as no target is confirmed. On the map side, it has its own 3D anchor and is only published (`candidate` state) after 4 consistent measurements. - **Phase 29 — voice: request and announcements (22/11, night)** — Two command modes: `prompt` (object set at launch, unchanged) and `stt` (the user says "je cherche ma gourde" — I'm looking for my bottle — with the phone's Talk button). Choices:
  1. **Recognition**: by default the phone *records* (MediaRecorder, stops after 0.9 s of silence) and the computer transcribes with Whisper-small (`transformers`, ~0.6 s per sentence, 1 GB downloaded on first use, loaded in the background at startup).   2. **Speech synthesis**: on the phone (`speechSynthesis`, unlocked in the Start gesture), so in the headset, with no extra network latency.
